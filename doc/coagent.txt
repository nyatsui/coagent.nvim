1. INTRODUCTION                                          *coagent-intro*

coagent.nvim runs a multi-step coding agent (investigate, edit, run
checks, fix, report) inside terminal Neovim. Authentication and API access
are delegated to CopilotChat.nvim v4 (main branch); no Copilot CLI and no
extra API keys are used. See README.md (English), README_ja.md (Japanese)
and docs/manual.md for details.

Requirements: Neovim 0.11+, CopilotChat.nvim v4, plenary.nvim.
Check the setup with |:checkhealth| coagent.

2. COMMANDS                                           *coagent-commands*

:Coagent [task]          Open the panel or send a task. With a range the
                              selection is attached (#selection).
                              ":Coagent /explain" runs a template.
:CoagentPlan [task|approve|discard]
                         Start a task in the plan phase, or approve /
                              discard the plan waiting for approval
                              (|coagent-plan|). With a range the selection
                              is attached; without a task the next message
                              starts in the plan phase.
:CoagentSkills [enable|disable <name>|reload]
                         List the Agent Skills, or enable / disable one
                              for this session (|coagent-skills|).
:CoagentExp [show|diff|note|compare|run ...]
                         The experiment log (same as /exp;
                              |coagent-experiments|).
:CoagentLedger [init|refresh[!]|note|decision|update|review|log|open|bundle|info]
                         The project ledger (same as /ledger;
                              |coagent-ledger|).
:CoagentDelegate <kind> [instruction] | list | open | cancel | detach
                         Bundle a subtask for another chat (same as
                              /delegate; |coagent-delegate|).
:CoagentReceive [id] [paste|clipboard|files]
                         Import its result (same as /receive).
:CoagentPrompt [name] [text]
                         Run a prompt template (|coagent-templates|).
                              With a range the selection is attached;
                              without a name pick one from a list.
:[range]CoagentInline [instruction]
                         Rewrite the selected lines in place with ONE
                              request (no tools), previewed in the buffer
                              (|coagent-inline|). Without an instruction
                              it is asked for; without a range the
                              current line is used.
:CoagentToggle           Toggle the panel.
:CoagentStop             Stop now (abort request, kill command, drop
                              pending approval).
:CoagentPause            Pause after the current step.
:CoagentResume           Resume a paused/interrupted/restored task. After a
                              limit pause the counters start fresh
                              (|coagent-limits|).
:CoagentApprove[!]       Approve the pending action (! = always), or the
                              plan waiting for approval.
:CoagentDeny[!] [reason] Deny (! = deny and stop); discards a waiting plan.
:CoagentReview           Review the pending edit hunk by hunk.
:CoagentChanges          List files changed by the agent.
:CoagentDiff             Diff of all agent changes.
:CoagentRevert [path|all] Revert agent changes.
:CoagentRewind           Rewind code and/or conversation to before a past
                              prompt. See |coagent-rewind|.
:CoagentFormat [mode]    Format the files the agent changed in this
                              session: changed (default, only the agent's
                              lines) | file. See |coagent-format|.
:CoagentOutput           Show the last command output.
:CoagentMode [mode]      supervised | readonly | auto | judge
:CoagentJudge [log [n]|clear]
                         Judge mode: list the judge's decisions / forget
                              cached verdicts. See |coagent-judge|.
:CoagentModel            Pick a tool-calling capable model (per role when roles are on).
                         Models with `usage.rates` show their price per 1M tokens.
:CoagentRoles [preset]   Model roles: single (default) | advisor | explorers | full
:CoagentEffort [level] [role]
                         Reasoning effort for this session: minimal | low |
                              medium | high | off | default, optionally for
                              one role. See |coagent-effort|.
:CoagentNew              New session.
:CoagentSessions         Restore a saved session of this project.
:CoagentLayout [layout]  vertical | float
:CoagentBudget [kind] {n}
                         Token budgets for this session: tokens (per task),
                         credits (per task, needs usage.rates), session; n
                         like 200000 / 200k / 1m, or off / default. Reaching
                         one pauses the agent (/resume continues with a fresh
                         budget; running training keeps going). Config:
                         limits.max_task_tokens / max_task_credits /
                         max_session_tokens, limits.budget_counts.
                         "month {n|off|default}" sets the monthly credit
                         budget for every instance and project until the
                         month ends (|coagent-monthly|).
:CoagentWidth [spec]     Panel width: N (columns), N%, +N, -N, reset. A width
                         set by hand (mouse, <C-w><, :vertical resize, < / >
                         in the panel) is remembered across reopen, terminal
                         resizes and restarts (`ui.remember_size`).
:CoagentUsage [billing]  Copilot quota, plus requests/tokens of the last task
                              and the session (|coagent-usage|). "billing"
                              opens the GitHub billing page in the browser.

                                                         *coagent-usage*
Usage. Copilot bills tokens as AI credits (1 credit = $0.01) at per-model
prices per 1M tokens (input, cached input, cache write, output). While a task
runs the status bar shows its requests, total tokens and the prompt-cache hit
ratio ("6req 48k c91%"; dropped first when the panel is narrow). Each model
response shows its breakdown in the timeline, e.g.
"in 12k (cached 11k, 92%) · out 450 · reasoning 300" (tool-call-only
responses: above their first tool item); a low cached share means the cache
missed and the whole history was read again. The breakdown is read from the
usage the API returns (the request is not changed); responses without it show
"cache not reported". `usage.show_request_usage = false` hides the per-response
lines. The task-completed item and :CoagentUsage show totals and breakdowns for
the last task and the session (per model). Exact numbers are on
https://github.com/settings/billing, which ":CoagentUsage billing" (or
"/usage billing") opens with |vim.ui.open()|; no billing API is called and no
extra token is used.

Credit ESTIMATE (optional): coagent does not fetch prices. Copy them from
GitHub's "Models and pricing" page (USD per 1M tokens) into `usage.rates`; the
status bar, the completed item and :CoagentUsage then add
"≈N credits (estimate)" and :CoagentModel shows the price. >lua
  usage = {
    rates = {
      ['claude-sonnet-4.6'] = { input = 3.00, cached = 0.30, cache_write = 3.75, output = 15.00 },
      ['gpt-5-mini'] = { input = 0.25, cached = 0.025, output = 2.00 },
    },
  }
<
credits = ((input - cached - cache_write) * input_price + cached * cached_price
  + cache_write * cache_write_price + output * output_price) / 1e6 * 100.
Missing prices fall back to `input`. Responses without a breakdown are priced
at the input rate and labelled "rough estimate". Long-context surcharges are
not modelled. The older `{ per_1k_tokens = n }` form still works.

                                                       *coagent-monthly*
Monthly budget. coagent adds the estimated credits and the tokens of every
model response (all roles) to a per-month file shared by every session,
project and Neovim instance:
  stdpath('state')/coagent/usage/<YYYY-MM>.json   (folder 0700, file 0600)
with totals per model and per project. The month starts on
`usage.month_start_day` (default 1; 31 = the month's last day) at midnight
local time; <YYYY-MM> is the month the period starts in. Each write reads the
file, adds, and replaces it atomically (temp file + rename), so it is always
complete JSON; two instances writing at the same moment can lose one
increment (accepted: the totals are an estimate). >lua
  limits = {
    max_monthly_credits = 1900, -- estimated credits per month (needs usage.rates)
    max_monthly_tokens = nil,   -- tokens per month (budget_counts); no rates needed
  }
<
When this month's estimate reaches a budget the agent pauses at the next step
boundary (reason 'limit'); background training keeps running. One notice at
`limits.budget_warn_at`. The month does not restart on /resume: raise the
budget with "/budget month {n}" or turn it off for the month with
"/budget month off" first. That override is global: it is stored in the month
file and ends with the month ("default" goes back to the config).
/budget and :CoagentUsage show "this month (estimate): 312 / 1900 credits,
since 2026-10-01"; the status bar shows "mo 312/1900cr" while a monthly budget
is set. It counts only coagent's own requests (not VS Code, CopilotChat chats
or other tools), and credits are an estimate from `usage.rates`; exact numbers
are on GitHub's billing page (":CoagentUsage billing"). Without usage.rates
there is no credit estimate: /budget and :CoagentUsage say so,
max_monthly_credits does not apply and max_monthly_tokens (if set) does.

`ui.show_multiplier = true` shows the legacy request-billing multiplier
("(legacy x1)") in the model picker; it does not describe token billing.

                                                        *coagent-effort*
Reasoning effort. Not sent by default. Set it in the config or per session:
>lua
  reasoning_effort = 'medium',     -- nil | 'minimal' | 'low' | 'medium' | 'high'
  roles = {
    explorer_effort = 'low',       -- per role; 'off' = never send for it
    advisor_effort = 'high',
  },
<
"/effort high" sets it for every role in this session, "/effort low explorer"
for one role, "/effort off" stops sending it and "/effort default" goes back
to the config (:CoagentEffort takes the same arguments; without one it opens
a picker). Session overrides are saved with the session. Order: session role
> session > config `roles.<role>_effort` > config `reasoning_effort`.

The status bar shows "effort:high" next to the model and :CoagentUsage lists
the effort of each role and how often each level was sent.

Higher effort spends more reasoning tokens (cost / quota) and time. The
"auto" model ignores it (the server picks the model). When CopilotChat lists the
levels a model advertises (CopilotChat PR #1585), the nearest supported level
is used, with a notice. A 400 that rejects the parameter is retried once
without it and the model is not sent an effort again until Neovim restarts
(never retried on 401/403). Only the request body changes: headers, auth,
client identity and URLs stay CopilotChat's.

3. PANEL KEYS                                             *coagent-keys*

  a  approve          A  approve always     d  deny (with reason)
  D  deny and stop    r  review hunks       gd diff
  <Tab>/za details    <CR> open details     gf jump to change
  gc changes          ]] [[ next/prev item   <C-c> stop (|coagent-queue|)
  p  pause            R  resume             gs sessions
  gn new session      gm mode               i  input
  q  close            g? help               gi revise the plan

While a plan waits for approval, a / ga approve it, d / gx discard it.
Input: <CR> (normal) / <C-s> (insert) send (queued while the agent works),
<C-c> take back queued messages, else stop, <C-k> panel,
<C-p>/<C-n> history, /help slash commands (|coagent-slash|). All keys are
configurable via `keymaps`.

                                                     *coagent-references*
References in a prompt attach context:

  @path               A workspace file (same as #file:path). "@dir/"
                      attaches a directory listing. Only an "@" at the
                      start or after whitespace counts, and only when the
                      path exists, so a@b.com or "@Override" stay as typed.
                      The path stays in the prompt text.
  @buffer @selection  Aliases of #buffer / #selection (a file of that
                      name wins).
  #buffer #buffers    Current buffer / all listed buffers.
  #selection          Visual selection the command was started with.
  #file:path          A file.
  #diagnostics        LSP diagnostics of the current buffer.
  #gitdiff[:staged]   Uncommitted (or staged) diff.
  #url:https://...    A web page, fetched with GET and attached as text
                      (clipped to `references.url_max_bytes`, 32 KB).
  #clipboard          The + register (else the unnamed register), clipped
                      to `references.clipboard_max_bytes`.

#url fetches only URLs you type: no approval is asked because it is a
fetch, not a send. Only http:// and https:// are accepted; other schemes,
a missing scheme and credentials (user:pass@host) are refused. It reuses
CopilotChat's resources.get_url (lynx -dump, else curl -L with HTML
stripped) and adds no cookies or auth headers. The URL and size appear in
the timeline; the page is untrusted data like any attachment. Disable it
with `references = { url = false }`. The model has no web-fetch tool of its
own (a URL it chose could leak workspace data in its query string).
Typing "#" pops up the reference names.

Files outside the workspace (symlinks resolved) and protected files
(`auto.protected_globs`: .env, keys, .git, ...) are refused with a warning.
Typing "@" pops up workspace files (git ls-files plus untracked files that
are not ignored, else a directory walk; protected files hidden; at most
2000), fuzzy-filtered as you type. Disable the popup with
`ui.mention_complete = false` (<C-x><C-o> still works).

4. SLASH COMMANDS                                        *coagent-slash*

A prompt whose first word is /name runs a command locally; it is never sent
to the model. Typing "/" at the start of the input pops up the commands
(also <C-x><C-o>; disable the popup with `ui.slash_complete = false`).
Commands go into the input history like prompts.

  /compact            Elide every long tool output before the last 8
                      messages now. Local only: no request.
  /compact summary    Ask the current model ONCE to summarize the older
                      turns into one message (one model call, billed by
                      tokens; <C-c>
                      cancels it).
  /plan [task]        Plan first (|coagent-plan|). "/plan approve" and
                      "/plan discard" act on the plan waiting for
                      approval.
  /go <task>          Run a task without the plan phase (plan.default).
  /skills [enable|disable <name>|reload]
                      List the Agent Skills; enable or disable one for
                      this session (|coagent-skills|).
  /skill <name> [task]
                      Run a task with a skill loaded up front.
  /exp [show|diff|note|compare|run ...]
                      The experiment log: table, details, diff, notes,
                      Markdown comparison, record a run
                      (|coagent-experiments|; local, no request).
  /ledger [init|refresh[!]|note|decision|update|review|log|open|bundle|info]
                      The project ledger (|coagent-ledger|; only init,
                      refresh and update send a request).
  /delegate <kind> [instruction] | list | open | cancel | detach
  /receive [id] [paste|clipboard|files]
                      Delegate a subtask to another chat you operate and
                      import its result (|coagent-delegate|; local).
  /new  /sessions  /model [role]  /mode [mode]  /roles [preset]
  /usage [billing]  /changes  /diff  /review  /stop  /processes
                      Same as the matching :Coagent* command.
  /effort <level> [role]
                      Same as :CoagentEffort (|coagent-effort|).
  /judge [log [n]|clear]
                      Judge decisions of this session / forget cached
                      verdicts (|coagent-judge|; local).
  /rewind             Same as :CoagentRewind (|coagent-rewind|).
  /format [mode]      Same as :CoagentFormat (|coagent-format|).
  /resume             Same as :CoagentResume (|coagent-limits|).
  /queue [clear]      List the messages queued while the agent works;
                      "clear" discards them (|coagent-queue|).
  /clear              Clear the input.
  /help               List the commands in the timeline.

Unknown commands show an error and keep the text. Start with "//" to send a
literal "/" ("//help me" sends "/help me"). Text whose first word is not a
command name (e.g. "/etc/hosts is wrong") is sent as a normal prompt.

/compact is refused while the agent is working. The session history itself
is not changed; only what later requests send. Because the start of the
request changes, the next request is a one-time prompt-cache miss.

                                                   *coagent-plan* *:CoagentPlan*
Plan first: check the direction before anything changes (like Claude Code's
plan mode). >

  /plan add a --dry-run flag to the export command
  /plan                 " the next message starts in the plan phase
<
The plan phase restricts the task to the read, search, LSP and explore tools
(like read-only templates): edit and command tools are not offered and are
refused if called. The winbar shows "plan". The model investigates and ends
with a plan (steps, files to change, verification, risks), shown as a plan
item; the winbar shows "plan ready" and an "approval" notification is sent
(|coagent-notify|). Then:

  approve   a (panel), ga (input), /plan approve, :CoagentApprove
            Appends "Plan approved. Execute it now." to the same
            conversation and runs it in the session's own mode
            (supervised still asks for every edit and command).
  revise    gi (panel), or type feedback and send it. Continues the plan
            phase; the revised plan replaces the old one.
  discard   d (panel), gx (input), /plan discard, :CoagentDeny
            Leaves the plan phase; nothing was changed.

The approval never raises the permission mode. The history stays
append-only; the plan phase offers fewer tools and a plan section in the
system prompt, so the first request after approving is a one-time
prompt-cache miss. With the advisor role (:CoagentRoles, roles.advisor.on_plan), its
PLAN review checks the written plan before you see it; the advice is shown
under the plan, goes with the approval, and the usual PLAN review before
the first edit is skipped.

<C-c> stops a planning task but stays in the plan phase; /plan discard
leaves it. `plan = { default = true }` starts every new task in the plan
phase; "/go <task>" skips it for one task (read-only templates never plan).
The plan phase is saved with the session, and |coagent-rewind| to a prompt
inside it restores it (rewinding "/plan approve" makes the plan wait for
approval again).

                                                *coagent-inline* *:CoagentInline*
Inline edit: rewrite a selection without the panel (like Copilot inline chat
or codecompanion's inline assistant). >

  :'<,'>CoagentInline handle the error instead of ignoring it
  vim.keymap.set('x', '<leader>ai', ':CoagentInline<CR>')
<
`keymaps.global.inline = '<leader>ai'` sets that mapping (visual: the
selection, normal: the current line).

ONE request is sent: no tools, no agent loop. It contains the instruction,
the selected lines, `inline.context_lines` (default 40) lines of context
before and after, the file path and the filetype, and asks for the
replacement of exactly the selected lines in one fenced code block. It uses
the builder model and reasoning effort and counts in the usage stats.

The reply is previewed in the buffer: changed lines are highlighted as
deleted and the new lines are shown as virtual lines below them. While the
preview is open these buffer-local keys exist (`inline.keymaps`; earlier
buffer-local mappings are restored afterwards):

  ga    Accept: edit the buffer (one undo step; the file is NOT saved).
  gr    Reject (cancels the request while it is still running).
  gi    Follow-up instruction; the last reply is sent along. Empty input
        just retries.
  gd    Side-by-side diff of the whole file in a new tab.

Without a code fence the whole reply is used, an unclosed fence takes the
rest of the reply (both are flagged in the preview); an empty block deletes
the selection.

The edit works on the live buffer, unsaved changes included. An accepted
edit is recorded as an agent change (baseline = the buffer right before it),
so it shows in :CoagentChanges / :CoagentDiff, can be reverted with
:CoagentRevert, and adds a checkpoint "[inline] path: instruction" to
|coagent-rewind|. While the buffer still holds exactly that unsaved result,
reverting or rewinding updates the buffer and leaves the disk alone.

The selection is tracked with an extmark, so edits elsewhere only move it.
If the selected lines themselves changed while waiting, nothing is applied;
`gi` retries with the current lines.

Permissions: readonly mode refuses (checked again on accept). In supervised
and auto mode the preview is the approval. Protected files and files
outside the workspace ask before anything is sent, as edit_file does;
`.git/` is refused. Not available while the agent is working (CopilotChat
tracks one request at a time).

                                                        *coagent-rewind*
Every prompt records a checkpoint (conversation length, timeline position
and the change tracker's state), saved with the session. /rewind and
:CoagentRewind pick a past prompt, then what to rewind:

  Code and conversation  Drop the prompt and everything after it, and
                         restore the files the agent wrote after it.
  Conversation only      Drop the conversation; files stay as they are.
  Code only              Restore the files; keep the conversation (the next
                         prompt tells the model the files were rewound).

Rewinding the conversation puts the prompt text back into the input. A
`/compact` summary or watermark that reaches past the cut is reset.

Only files the agent wrote after the prompt are touched. Each goes back to
its content right before the agent's first write after the prompt, so edits
you made before that write are kept. A file changed outside the agent since
its last write is a conflict and you are asked, as with :CoagentRevert:
keep your edits (skip the file), discard them, or cancel. If an affected
file has an unsaved buffer nothing is rewound (unless the unsaved text is
exactly a recorded inline edit: then the buffer is restored). Rewinding is
refused while the agent is working. Accepted inline edits add checkpoints
too; rewinding to one puts nothing back into the input.

                                                        *coagent-format*
Formatting of agent-edited files (ALEFix-like). Nothing is formatted
automatically by default.

  format_after_edit = false     Default. Never automatic; use /format.
  format_after_edit = 'changed' After each write_file/edit_file, format only
                                the lines that differ from the agent's
                                baseline.
  format_after_edit = 'file'    After each edit, format the whole file.
  format = { timeout_ms = 2000, filetypes = nil }
                                `filetypes` (e.g. { 'python' }) limits
                                formatting to those filetypes.

/format [changed|file] and :CoagentFormat [changed|file] format every file
the agent changed in this session ('changed' by default) and show a summary
(formatted, already formatted, skipped and why). Refused while the agent is
working.

Formatter: conform.nvim when installed, called with `lsp_format =
'fallback'` and your `formatters_by_ft`; otherwise a language server
attached to the buffer that supports formatting; otherwise nothing (skipped
silently). In 'changed' mode only line ranges are formatted. conform applies
only the formatter's hunks that overlap the range, even for formatters
without native range support. With a language server that cannot format
ranges the file is skipped with a note, and never widened to the whole file.

The file is loaded into a hidden buffer, or an open buffer is reused when it
has no unsaved changes. Files with unsaved buffer edits, protected files
(`auto.protected_globs`), files outside the workspace and files edited
outside the agent since its last write are never formatted. The result is
written to disk and recorded as an agent change: diff, review, revert and
/rewind include it, and the baseline stays the content before the agent.
After an automatic format the tool result tells the model "the file was
auto-formatted (N lines changed); re-read before further edits".

No extra approval is asked: you approved the edit itself, and formatting is
local and deterministic (your own formatter configuration).

Example with conform.nvim and ruff (manual formatting only): >lua
  require('conform').setup({
    formatters_by_ft = {
      python = { 'ruff_fix', 'ruff_organize_imports', 'ruff_format' },
    },
  })
  require('coagent').setup({ format_after_edit = 'changed' }) -- or false
<
                                              *coagent-diagnostics-after-edit*
After a successful write_file/edit_file (and auto-format), coagent waits
briefly for the language servers and appends only the diagnostics the edit
introduced to the tool result: >text
  Edited app/models.py (+3 -1)
  Diagnostics after this edit (new):
  app/models.py:42:12 [Pyright] "user_id" is not defined
<
The timeline shows the count on the tool line ("1 new error").

  diagnostics_after_edit = {
    enabled = true,          false (or diagnostics_after_edit = false): off
    min_severity = 'error',  'warn' also reports warnings ("warning: ...")
    timeout_ms = 1500,       wait for a report on the new content
    max_items = 10,          cap on reported diagnostics
    max_bytes = 2000,        cap on appended bytes ("[N more not shown]")
  }

"New" means: when the file was loaded before the write, compared with a
snapshot of its diagnostics by message+source+code, ignoring lines; when it
was not loaded, only diagnostics on the lines the agent changed (a created
file: all). Nothing is appended (no tokens) when nothing is new, no server
is attached, or the server does not report within timeout_ms (a server
that is still starting may miss the first edit of a file).

The file is loaded into an unlisted hidden buffer when needed (as the LSP
tools do) so your autostart attaches the server, and stays loaded; an open
unmodified buffer is reloaded so the server sees the new content. Files
without a filetype are skipped, and a hidden buffer no server attached to
is closed. The wait is woken by |DiagnosticChanged| and yields the task
coroutine, so the UI never blocks. Buffers are never modified; files with
unsaved buffer edits are refused before the write, as always.

                                                     *coagent-templates*
Prompt templates run as /name [text] (or :CoagentPrompt name [text]). The
template text is put before yours, and #selection (started from visual
mode) or #buffer is attached unless your text names a source.

  /explain            Explain the code.                      (read-only)
  /codereview         Review the code for problems.          (read-only)
  /fix                Find, fix and verify the problem.
  /optimize           Improve performance and readability.
  /docs               Add documentation comments.
  /tests              Write tests and run them.
  /commit             Commit message for #gitdiff:staged.    (read-only)

/review stays the hunk review of a pending edit; /codereview is the code
review. A read-only template limits only its own task to read/search tools
(the bar shows "read-only (task)"); the mode returns afterwards. Templates
never raise the permission mode. Unknown names are not sent.

User templates come only from the config (never from repository files):
>lua
  prompts = {
    Summarize = { prompt = 'Summarize this code.', mode = 'readonly',
                  description = 'Short summary' },
    Tests = false,          -- remove a built-in
  }
<
Names are case-insensitive and become lower-case commands (/summarize).
`mode` accepts only 'readonly'. `context = false` skips the automatic
#selection/#buffer. A template named like a built-in command (/review)
is reachable only through :CoagentPrompt.

                                                        *coagent-skills*
Agent Skills are folders with a SKILL.md (YAML front matter with `name`,
`description` and optional `allowed-tools`, then Markdown instructions),
plus any reference files or scripts: the format of Claude Code and VS Code
Copilot, so community skills work by copying their folder.

  skills.paths        Your skills (default ~/.config/coagent/skills):
                      trusted like your config.
  skills.repo = true  Also .github/skills/, .claude/skills/ and
                      .agents/skills/ of the repository: UNTRUSTED,
                      lower-priority notes like AGENTS.md.

Progressive disclosure keeps requests small and the prompt cache warm:
1. The system prompt lists only "- name: description" of each enabled
   skill, sorted by name and capped (`max_listed`, `max_description`).
   The list is fixed for the whole task.
2. The model calls use_skill(name) when a task matches; the timeline
   shows "skill: <name>". It returns the SKILL.md body and the list of
   the skill's files.
3. The model reads those files with read_file. Files of YOUR skills are
   readable outside the workspace without approval, read-only (protected
   names such as .env still ask; writes are refused).

Nothing in a skill changes permissions, the model or the mode. Only name,
description and allowed-tools are read from the front matter.
`allowed-tools` (Claude Code names such as Read, Edit, Bash(git log:*), or
coagent tool names) only NARROWS the file-change and command tools for the
rest of the task; reading and searching stay available and nothing is
pre-approved. Scripts in skills are never run by coagent: the model can
only use run_command, which asks like any command (in auto mode a command
that references a skill folder is never auto-approved). A repository skill
folder that symlinks outside the workspace is ignored. With duplicate
names the first wins: your folders, then .github, .claude, .agents.

/skills lists every skill (source path, user/repo, enabled) and the
skipped SKILL.md files, and picks one to enable/disable for this session
(saved with the session; applies from the next task). "/skills reload"
re-scans the folders. "/skill <name> [task]" attaches the skill to the
task message up front; its allowed-tools also shrink that task's tool list.
>lua
  skills = { enabled = true, paths = { '~/.config/coagent/skills' },
             repo = true, max_listed = 50, max_description = 200 }

                                                    *coagent-experiments*
The experiment log records ML training / evaluation runs and their metrics
per project, so runs can be compared and handed to a web chat or to the
agent without requests. Nothing in it sends a model request.

A command that runs through run_command or start_process is recorded
when (whatever the entry point is called):
1. the agent marks it: both tools take `experiment = true` and an optional
   short `name`; the system prompt asks for it on every training /
   evaluation run (bash scripts/run.sh, python -m pkg.train, make sweep);
2. it starts like an entry command of the project ledger: the commands in
   backticks under "How to run" in overview.md become prefix matches (the
   program and its entry script or module, e.g. "bash scripts/run.sh",
   "python -m vision.train", "torchrun ... -m vision.train"; setup / test
   commands are skipped), re-read when the ledger changes
   (`experiments.from_ledger`);
3. it matches `experiments.commands` (Lua patterns, an extra; default:
   python scripts with train / eval / test in the name, python -m ...train
   / ...eval, and the launchers torchrun, accelerate launch, deepspeed,
   python -m torch.distributed.run / accelerate.commands.launch);
unless it matches `exclude` (pytest, unittest) and was not marked. Every
"/exp run <command>" is recorded too. Stored:
id, time, command, cwd, source (agent, agent:bg, user), run name, how it
was recognized, git HEAD and
branch, a short hash of `git diff HEAD` (the diff itself up to
`max_diff_bytes`), changed files, untracked names, duration, exit code,
the output tail, settings from the command line (--lr 1e-3, --epochs=10,
LR=0.1, model.lr=0.01) and metrics:
- `key=value` / `key: value` for the names in `metrics` (loss, val_loss,
  acc, accuracy, f1, auc, mae, rmse, epoch, lr), also with a prefix from
  `metric_prefixes` (val_acc, train/loss, test-f1);
- numeric fields of output lines that are JSON objects (`json_lines`);
- your `patterns`: "Lua pattern with (key) and (value)" or
  { pattern = '...(value)...', key = 'name' };
- files the run wrote, `log_files` globs relative to the run's cwd (only
  files modified during the run, the newest per pattern): CSV/TSV, JSON
  (object or array of objects), JSONL.
The LAST value per key wins. Foreground runs are recorded on exit (the
result ends with "[experiment #N recorded: ...]"); background runs when the
process exits, with a notice in the panel.

                                                    *coagent-wait-process*
Long runs are hands-off. run_command stops at `commands.max_timeout_ms`
(15 minutes); for training / evaluation that may take longer the agent
calls start_process (experiment = true) and then
`wait_process(id, until, timeout_ms)`. It blocks inside the tool until the
process exits (until = "exit", the default), a Lua pattern appears in its
new output, or (experiment runs) a monitoring checkpoint comes
(|coagent-monitor|). While it waits no
model request is made (the prompt forbids polling read_process_output),
the tool item shows the runtime and the last output line, and the wait is
not counted toward `limits.max_duration_ms`. <C-c> / :CoagentStop stops
the task and the run; p / :CoagentPause only stops waiting (the run keeps
going; /resume waits again). The result has the exit code, the tail of the
new output and the experiment's metrics line. wait_process changes nothing
and needs no approval; start_process asks like run_command.

                                                        *coagent-monitor*
Monitored runs: instead of a fixed lifetime the model decides from the
training log whether a run continues. While an experiment run goes, its
metrics are kept as a per-step / per-epoch series (in memory, and capped,
`max_points` per metric, in the experiment entry for later comparisons).
wait_process on the run returns to the model only at a checkpoint:
  - `check_every_ms` (default `experiments.monitor.interval_ms`, 20 min)
    passed AND new metrics arrived;
  - an anomaly, detected deterministically and reported once each: NaN/Inf
    in a loss, a loss above `divergence_factor` (3) x its recent minimum,
    "CUDA out of memory", a Python traceback, no output for `stall_ms`
    (30 min) (`on_events = false` turns these off for one wait);
  - the process exited.
The result has the reason, runtime, progress and ETA (Epoch 3/10, step
1200/50000, tqdm bars, --epochs), one trend line per metric (last 5
points, best so far, points since the best, slope, NaN/Inf), the best
previous run at the same epoch / step, the last 20 output lines and
"decide: call wait_process again to continue, or stop_process with a
reason". The system prompt tells the model to stop on NaN / divergence,
an error or traceback, no improvement of the validation metric for
`patience` evaluations (unless warmup or a restart makes one plausible),
a run clearly worse than the best run at the same epoch, or a ledger goal
already reached; otherwise to continue; always with the reason.
`stop_process(id, reason)` records "stopped by agent: <reason>" as an /exp
note and in the ledger, shows a notice and sends the 'stopped'
notification. Stopping the agent's own run needs no approval.

Limits: experiment runs have no lifetime cap while monitoring is on
(`background.max_lifetime_ms` still applies to other processes);
`experiments.monitor.max_hours` is an optional absolute net (default
none). Cost in tokens: waiting costs nothing; each checkpoint costs the
input tokens of the conversation (mostly cached) plus about 1-3k new
tokens and a short answer. The answers to checkpoints of one wait chain
count as a single step of `limits.max_steps`; checkpoint returns do not
count toward `max_tool_calls` and their time is not counted toward
`max_duration_ms`. If a task pauses at a limit anyway, /resume continues
and the agent waits again (the run keeps going).

`/exp watch [id]` hands a running /exp run process to the agent (a task
with the same rules; it may stop the run with a reason). `/exp unwatch
[id]` ends monitoring without killing the process: a waiting wait_process
returns and the agent may no longer wait for or stop it. Without /exp
watch the agent cannot stop a run you started.

Storage: stdpath('state')/coagent/experiments/<project>-<hash>.jsonl,
outside the repository, directory 0700, file 0600, secrets masked.
Append-only (last record of an id wins), compacted automatically, at most
`max_entries` runs.

  /exp                Table in a scratch buffer: id, time, status,
                      duration, command, key metrics as
                      "value Δprev/Δbest" ("*" = best run), last note.
                      <CR> details, D diff vs the previous run, c copy
                      the comparison, R refresh, q close.
  /exp show <id>      Details (Markdown) with the diff and output tail.
  /exp diff <a> [b]   Difference between the recorded diffs of two runs
                      (one id: vs the run before it).
  /exp note <id> <text>
                      Add a note to a run.
  /exp compare [ids]  Compact Markdown comparison into the + register
                      (unnamed register without a clipboard): metrics
                      (best in bold), differing settings, common
                      settings, commands, code summary, notes. Without
                      ids: the last `compare_runs` runs plus the best.
  /exp run <command>  Run in the background and record it. The usual
                      approval of start_process applies (asks in
                      supervised mode, refused in read-only mode).
  /exp watch [id]     Hand a running /exp run to the agent for
                      monitoring (|coagent-monitor|); needs an idle agent.
  /exp unwatch [id]   End the agent's monitoring; the run keeps going.

"Best" is the highest value, the lowest for names in `lower_is_better`
(loss, mae, rmse, ...); `neutral` names (epoch, lr, step) only show the
change vs the previous run. The agent reads the log with the read-only
`experiments` tool: no query = the compact table, "12" = one run's
details (no full diff), "compare" or "3 7" = a comparison, other text =
runs whose command or notes contain it.
>lua
  experiments = {
    enabled = true,
    from_ledger = true,  -- "How to run" commands of the ledger mark runs
    commands = { 'python[%d%.]*%s.-train[%w_%-%.]*%.py', 'torchrun%s' },
    exclude = { 'pytest' },
    metrics = { 'loss', 'val_loss', 'acc', 'f1', 'epoch', 'lr' },
    patterns = {}, json_lines = true,
    log_files = { 'lightning_logs/*/metrics.csv' },
    columns = nil, max_columns = 5, primary = nil, compare_runs = 5,
    max_diff_bytes = 100 * 1024, max_output_tail = 8 * 1024,
    max_entries = 500,
    monitor = {                      -- |coagent-monitor|
      enabled = true,
      interval_ms = 20 * 60 * 1000,  -- checkpoint interval
      stall_ms = 30 * 60 * 1000,     -- no output this long = anomaly
      patience = 3,                  -- evaluations without improvement
      divergence_factor = 3, divergence_window = 50, min_points = 5,
      worse_margin = 0.05,           -- "clearly worse" than the best run
      max_hours = nil,               -- optional absolute net (nil = none)
      max_points = 100, trend_points = 5, tail_lines = 20, max_keys = 8,

                                                        *coagent-ledger*
The project ledger is the single source of truth about the ongoing work of a
project, kept by coagent across sessions: what the code does, the goal, what
was decided and why, what each subtask did and where things stand. Local
tasks start from it, and other chats you delegate a subtask to can get it
whole (|coagent-ledger-bundle|).

Files (Markdown with stable "## " headers; you edit them, coagent updates
them):
  overview.md   Purpose, Directory tree, Files (each file's role), Data flow
                (dataset -> dataloader -> model -> loss/optimizer -> train
                loop -> eval -> outputs), Configs and hyperparameters, How
                to run, Outputs and metrics.
  goals.md      Objective, Target metric, Constraints. Yours: never
                rewritten.
  status.md     Current state, Best results, Open issues, Next steps.
                Rewritten (not appended) by each update.
  decisions.md  Append-only: "### D-<n> · <date> · <title>" with decision,
                reason, rejected alternatives, source.
  subtasks.md   Append-only: "### S-<n> · <date> · <kind> · <title>" (kind
                local, delegated, experiment or note) with request, result,
                files changed, outcome.

Storage: stdpath('state')/coagent/ledger/<project>-<hash>/, outside the
repository, directory 0700, files 0600 (restored on every write). With
`ledger.dir_in_repo = '.coagent/ledger'` it is kept in the repository: add
`.coagent/` to .gitignore, or commit it to share it.

Requests (everything else is local):
- /ledger init: ONE request without tools. coagent reads the directory tree
  and the core files itself (README, pyproject / requirements, train /
  eval / model / dataset / loss / config sources, configs; up to
  `init_max_bytes`, `max_file_bytes` per file; protected files such as .env
  and binaries are skipped, secrets masked); the model writes overview.md.
  Files the overview names in `backticks` are fingerprinted (sha256, mtime).
- /ledger refresh: ONE request, only when a file listed in the overview
  changed or disappeared (a warning is shown once at the next task start).
  "/ledger refresh!" regenerates it anyway.
- After each finished task, imported result (|coagent-ledger-bundle|) or
  background experiment: ONE small request appends the subtask entry and
  any decisions and rewrites status.md (`auto_update`). Files changed and
  the outcome are written by coagent. If the request fails a plain entry
  is written and status.md is left alone. Only once the ledger exists.

  /ledger             Open goals.md and status.md in a split for editing
                      (creates the ledger) and show its state.
  /ledger open <file> overview, goals, status, decisions or subtasks.
  /ledger init        Generate overview.md (above).
  /ledger refresh[!]  Refresh it when stale (! = anyway).
  /ledger note <text> A note entry in subtasks.md (no request).
  /ledger decision <title> [-- reason [-- rejected alternatives]]
                      A decision entry (no request).
  /ledger update      Record the last finished task now (one request; for
                      `auto_update = false`).
  /ledger review      Pending updates of sections you edited: shows the
                      diff, then apply / keep yours / decide later.
  /ledger log [decisions|subtasks]
                      Recent `recent` entries in full plus one line per
                      older entry.
  /ledger bundle      The whole ledger as Markdown into the + register.
  /ledger info        Location, staleness, counts, pending updates.

Your edits win: coagent keeps a hash of every section it wrote; a section
whose text differs was edited by you and is never overwritten. The update
waits in the ledger's .meta.json until /ledger review. A file with unsaved
changes in a buffer is not written (appended entries wait for the save);
an open unmodified buffer is reloaded.

Digest: at the start of a local task a compact digest (goals, status, the
last `digest_decisions` decisions, at most `digest_max_bytes`) is appended
to the task's first message as <project_ledger rev="...">, as
lower-priority project notes. It is injected once per change and never
touches the system prompt, so the prompt cache keeps hitting; the task's
messages stay identical on every step. `inject = false` disables it.

Trust: the ledger holds model-written and repository-derived text. It is
context data and cannot change permissions, the mode or the model. Model
text cannot add sections or entries ("#" lines become bold text), secrets
are masked, and the digest cannot close its own block.

  ledger = {
    enabled = true,
    dir = nil,            -- nil = stdpath('state')/coagent/ledger
    dir_in_repo = nil,    -- e.g. '.coagent/ledger'
    auto_update = true, inject = true,
    model = nil, update_model = nil,   -- nil = the selected model
    recent = 10, digest_decisions = 5, digest_max_bytes = 6000,
    init_max_bytes = 160 * 1024, max_file_bytes = 24 * 1024,
    tree_max_entries = 300,
  }

                                                      *coagent-delegate*
coagent stays the orchestrator and hands heavy subtasks (result analysis
and planning, larger implementations, hard fixes, reviews) to ANOTHER chat
that you operate by hand (any web chat, e.g. Microsoft 365 Copilot). It
writes a self-contained bundle folder; you paste and attach it, and bring
the reply back with /receive. coagent never contacts, logs in to or
automates the other chat. Follow your organization's rules for what may be
pasted into external tools; protected files (auto.protected_globs) are
never included and files with token-like text are flagged first.

Kinds and output contracts (delegate.language = 'ja' for Japanese):
  analyze     Markdown with ## Findings / ## Hypotheses / ## Plan /
              ## Experiments (expected effect, exact commands).
  implement   ## Manifest table (path | modified/new/deleted | summary),
              EVERY changed or new file IN FULL as a download with the
              SAME file name (no "..." omissions), ## Verification.
  fix         ## Cause, then the same as implement.
  review      ## Findings by severity (### Critical / Major / Minor /
              Nit) with path:line.
  your own    delegate.kinds = { name = { output = 'text'|'files',
              description, contract, default_instruction } }
              (name = false removes a kind).

  /delegate <kind> [all] [instruction with @files]
      Writes <project folder>/<id>/ (|coagent-delegate-location|):
        00_prompt.md     to paste: id, kind, instruction, the attachments
                         and their meaning, the output contract
        01_ledger.md     the project ledger (|coagent-ledger-bundle|), or a
                         local overview when there is none
        02_sources.md    FULL source files: @files (folders too), files
                         changed in the session, core files of the ledger
                         overview; "all" = every file. Files beyond
                         max_source_bytes are left out WHOLE and listed.
        03_context.md    OS, Python, PyTorch/CUDA, nvidia-smi, git status
                         and diff, the last command outputs in full, the
                         experiment table
        bundle.md        01 + 02 + 03 in ONE file, unchanged, between
                         "===== BEGIN <file> =====" / "===== END <file>
                         =====" lines (delegate.combined = false: none)
        attachments      copies of @data files (CSV, logs, plots) as-is
        manifest_expected.json   paths + sha256 of the sources sent
      copies 00_prompt.md to the + register and adds a pending entry to the
      ledger. Attach EITHER bundle.md OR 01-03 (same content; 00_prompt.md
      tells the other chat both are possible) plus the attachments.
      The notice shows the folder relative to the repository
      (".coagent/delegate/3/"), the `latest` path and the full path; a
      dialog offers: y copy the folder path to the + register (paste it in
      the browser's file picker: macOS Cmd+Shift+G, Linux Ctrl+L, Windows
      the address bar), o open the folder (vim.ui.open; over SSH or without
      a UI the path is printed), p copy 00_prompt.md again.
      delegate.offer = false: no dialog; delegate.open_folder = true: open
      the folder right away.
  /delegate list | open <id> | cancel <id> | detach
      open: opens the bundle folder (prints it over SSH) and copies its
      path; the dialog offers p to copy 00_prompt.md again.
  /receive [id] [paste|clipboard|files]
      Imports the reply. Text: a paste buffer pre-filled from the +
      register (:w imports it). Files: downloads newer than the bundle in
      delegate.download_dir ($XDG_DOWNLOAD_DIR, xdg-user-dir, ~/Downloads)
      mapped by the reply's manifest, manifest_expected.json, then a unique
      workspace file of that name ("name (1).py": the newest wins; unknown
      names are asked about). Pasted "### path" full-file blocks and
      unified diffs are applied too. Every change goes through write_file /
      delete_file: diff, per-hunk review, approval (also in auto mode:
      delegate.review_imports), protected / unsaved checks, change
      tracking, |coagent-rewind|, |coagent-format|, new diagnostics.
      A file changed locally since the bundle (base drift) is shown and you
      choose: merge with the agent, overwrite after review, or skip.
      Snippets that cannot be placed deterministically go to ONE agent step
      (read + edit_file/write_file only). The result is recorded in the
      ledger and local follow-ups are offered (verification commands, one
      or all experiments from the analysis, the plan, review fixes). Their
      prompts ask for start_process (experiment = true) + wait_process for
      long commands and a report of the metrics.
      `delegate.auto_followup` = 'verify' | 'experiments' | 'first' starts
      the matching follow-up by itself after a clean import (every file
      applied, nothing denied; approvals follow the current mode); false
      (default), no match or a denied file: the selection is offered.

The agent can delegate with the `delegate` tool; it ALWAYS asks for
approval (also in auto mode) and shows the bundle summary. The task then
waits in WAITING_EXTERNAL (winbar "waiting: analyze #3", notify 'waiting',
saved with the session). New messages are refused until /receive 3 (the
result becomes the tool's result), /delegate detach (keep it for later),
/delegate cancel 3 or :CoagentStop.

                                                *coagent-delegate-location*
delegate.location chooses where bundles go:
  'repo' (default)  <root>/.coagent/delegate/<id>/. `.coagent/` is added
                    ONCE to .git/info/exclude (local to the clone, never
                    committed) unless git ignores it already; the shared
                    .gitignore is never touched; outside git nothing else
                    is written. With ledger.dir_in_repo inside .coagent/,
                    only .coagent/delegate/ is excluded.
  'home'            <delegate.home_dir, default ~/coagent>/<project>/<id>/
                    (outside the repository; no hidden folder).
  'state'           stdpath('state')/coagent/delegate/<project>-<hash>/<id>/
                    (the old location).
delegate.dir overrides it (<dir>/<project>-<hash>/<id>/). Every location
keeps a `latest` symlink to the newest bundle (skipped silently when it
cannot be made), so the picker path stays the same. Folders 0700, files
0600. Bundles in the other locations (e.g. the state folder of earlier
versions) stay in /delegate list, /delegate open and /receive; new ids
continue after them.

coagent never lists, searches, mentions, scans, diffs or sends `.coagent/`:
glob / search / list_dir skip it unless the path names it; @ completion,
02_sources.md and /delegate all, /ledger init / refresh and the stale
check, git_status / git_diff, 03_context.md and experiment records (git
pathspec ":(exclude).coagent"), format-after-edit and diagnostics leave it
out. `.coagent/**` is a default auto.protected_globs entry and the write
tools refuse it: only coagent writes bundles.

Example (ML): /delegate analyze why does val_acc plateau? @metrics.csv
@loss.png -> paste, /receive 4 -> run the suggested experiment locally ->
/delegate implement add a cosine schedule as planned in #4 @train.py ->
/receive 5 maps train.py from ~/Downloads and applies it after review.

                                                         *coagent-queue*
Messages sent while the agent is busy (responding, running a tool or waiting
for approval) are queued and shown at the bottom of the panel as
"Queued (n)". They never interrupt a running tool or an approval prompt:
at the next step boundary (after the tool results of the current step,
before the next request) they are appended as one user message labelled
"User (while you were working): ...". The history stays append-only, so
the prompt cache keeps working. If the task finishes first, the oldest
queued message starts a new task (with its own |coagent-rewind|
checkpoint). Read-only templates (/explain, ...) always wait for a task of
their own.

<C-c> in the input (or panel) first moves the queued messages back into
the input; press it again to stop the agent. /queue lists them and
/queue clear discards them. Stopping the task (:CoagentStop, deny & stop)
also moves them back into the input instead of sending them. Slash
commands are never queued; they run at once.

                                                        *coagent-notify*
When Neovim does not have focus, coagent rings the terminal bell on the
events in `notify.on`: >lua
    notify = {
      on = { 'approval', 'done', 'failed', 'limit', 'waiting', 'stopped' }, -- also: 'paused'
      bell = true,                -- BEL to the terminal (tmux: bell flag)
      desktop = false,            -- notify-send (Linux) / osascript (macOS)
      only_when_unfocused = true,
    }
<
Messages are generic status text only, e.g.
"coagent: approval needed (run_command)"; prompt, code and model output
are never included. Desktop notifications call a local command; nothing is
sent over the network. Focus is tracked with |FocusLost| and
|FocusGained|. Inside tmux this needs `set -g focus-events on`; without
focus events Neovim always counts as focused, so set
`only_when_unfocused = false` instead. No "done" notification is sent when
a queued message immediately starts the next task. 'limit' is sent when a
per-task limit pauses the task (|coagent-limits|); 'paused' covers the
other pauses (:CoagentPause, interruptions). A plan ready for approval
(|coagent-plan|) is sent as 'approval' ("approval needed (plan)"), not
'done'. 'waiting' is sent when a task starts waiting for a delegated
subtask (|coagent-delegate|). 'stopped' is sent when the agent stops a
monitored training run (|coagent-monitor|).

                                                        *coagent-limits*
Per-task limits are brakes against runaway loops: every request resends
the whole history, and Copilot bills by tokens. >lua
    limits = {
      max_steps = 40,                    -- model requests  } pause the
      max_tool_calls = 120,              -- tool executions } task
      max_duration_ms = 30 * 60 * 1000,  -- active time     } (resumable)
      max_consecutive_denials = 3,       -- end the task
      max_identical_calls = 4,           -- end the task
      max_identical_failures = 3,        -- end the task
    }
<
Reaching the step, tool call or time limit PAUSES the task (state PAUSED,
reason "limit") at a step boundary, when every tool call already has its
result. The panel says which limit, the usage so far and how to continue;
the status bar shows "paused (limit)". :CoagentResume, /resume or `R`
continues the same task and history with fresh counters; nothing is
re-run. /stop ends it; a new message starts a new task instead. Time spent
waiting for approval or in wait_process does not count. The answers to the
checkpoints of a monitored run count as one step (|coagent-monitor|). The pause is saved with the session
and can be resumed after restoring it (:CoagentSessions).

Denying `max_consecutive_denials` actions in a row, or the model repeating
the same call or the same failure, still ends the task: the user said no,
or the agent is looping.

5. MODES                                                 *coagent-modes*

readonly    Only read/search tools are offered and executed.
supervised  Reads run automatically; every edit and command asks first.
auto        Only for workspaces in `auto.workspaces` or explicitly enabled.
            Workspace edits and allowlisted simple commands run without
            approval (sandboxed when sandbox-exec/bwrap exists). Dangerous
            commands always ask.
judge       Only for workspaces in `judge.workspaces` / `auto.workspaces`
            or explicitly enabled (a separate confirmation from auto).
            Reads and workspace edits as in auto; commands are NOT
            sandboxed and are decided by hard rules, then a judge model.
            See |coagent-judge|.

Claude Code equivalents: supervised = default (ask), auto = accept edits +
a command allowlist, judge = auto mode (a model decides), /plan = plan mode.

                                                         *coagent-judge*
Judge mode ~

For hands-off runs where an allowlist is impractical (training entry points
vary) and the OS sandbox gets in the way (bwrap hides GPUs). Per tool call:

1. Hard rules, deterministic, never sent to the judge and never turned into
   "allow" by it. Always ask: dangerous patterns (rm, git reset / clean /
   checkout -- / restore / push / rebase, sudo, | sh, chown, chmod -R,
   publishing), network transfer (curl, wget, scp, ssh, nc, rsync to a
   remote), package installs (pip / conda / npm install, ...), unlink /
   rmdir / find -delete, crontab and services, arguments outside the
   workspace (/etc/..., ~/..., ../.., $HOME/...), protected files, skill
   scripts, deletes, writes outside `writable_globs`, reads outside the
   workspace or of protected files, the delegate tool and MCP tools.
   Whatever supervised denies is denied.
2. Reads inside the workspace run.
3. Workspace edits run (as in auto).
4. Any other command (run_command, start_process, complex shell) is sent
   to the judge: one headless request to `judge.model` (default: the
   builder model; a cheap model is recommended), no tools, temperature 0.
   It gets your request, the exact command, cwd, a command analysis, the
   agent's purpose / notes and the last tool actions. Everything not
   computed by coagent is wrapped in nonce-delimited DATA blocks that the
   judge must never take instructions from. The answer must be exactly
   {"decision": "allow"|"ask", "risk": "low"|"medium"|"high",
   "reason": "..."}; anything else, an error or a timeout asks you.

The verdict is a dim line on the tool item ("judge: allowed — runs the
project's training script"). Verdicts are cached per (command, cwd) for the
session. After `limits.max_consecutive_denials` "ask" verdicts in a row the
judge is paused for the rest of the task (every command asks you). Judge
requests count as role "judge" in :CoagentUsage. /judge log lists every
verdict with its outcome; the log is saved with the session.

Options: >lua
  judge = {
    model = nil, timeout_ms = 15000, workspaces = {}, cache = true,
    max_context_bytes = 8000,
    allowed_paths = {},       -- absolute paths args may name (datasets)
    notify_on_allow = false,  -- bell when a command ran without asking
  }
<
Trade-off: no OS sandbox (`commands.sandbox` is not applied), so GPUs work,
and an allowed command runs with your full user permissions. The judge can
be wrong; destructive, remote and outside actions stay behind rules it
cannot override. Use a version-controlled workspace and a branch.
